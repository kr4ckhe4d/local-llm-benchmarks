# DDR5 / 9800X3D — what faster host memory actually bought

Measured 2026-09-21, after the box moved from a Ryzen 9 5950X with 64 GB
DDR4-3200 to a Ryzen 7 9800X3D with 32 GB DDR5-6000.

**This file does not replace [README.md](README.md).** Every number there was
measured on the DDR4 box and is still the record of that machine. What follows
is the re-measurement of the tables that the host-memory change actually moves,
using the same method, so the two can be read side by side.

## Why this is a clean experiment

Only the CPU and the RAM changed. Everything else that could plausibly move a
throughput number is byte-identical:

| | DDR4 box | DDR5 box |
|---|---|---|
| CPU | Ryzen 9 5950X, 16C/32T, 64 MiB L3 | **Ryzen 7 9800X3D, 8C/16T, 96 MiB L3** |
| RAM | 64 GB DDR4-3200, 4 × 16 GB, all slots filled | **32 GB DDR5-6000 CL36, 2 × 16 GB, 2 of 4 slots** |
| GPU | RX 9070 XT, 16,304 MiB | *unchanged* |
| ROCm | `7.2.53211-3d9ef42` | *unchanged* |
| llama.cpp | `b10463` (`7c35571e5`) | *unchanged* |
| GGUFs | — | *unchanged, same files* |
| Kernel | 7.1.5 | 7.2.6 ← the one uncontrolled variable |

So a difference in these tables is a host-memory difference, with the kernel as
the single caveat. **VRAM-fit rows are unaffected and were not re-run** — the
card did not change, and `-ncmoe 12` still fails to allocate exactly as before.

### Memory config

Two matched DIMMs, one per channel, other two slots empty:

| Slot | Module | Rated | Running |
|---|---|---|---|
| CHANNEL A, DIMM 1 | Crucial Pro `CP16G60C36U5B` | 6000 CL36 | 6000 |
| CHANNEL B, DIMM 1 | Crucial Pro `CP16G60C36U5B` | 6000 CL36 | 6000 |

`dmidecode` reports `Speed: 5600 MT/s` (the JEDEC SPD fallback) against
`Configured Memory Speed: 6000 MT/s`, so EXPO is applied and holding.

**Leaving two slots empty is deliberate, and it is the opposite of the old
box.** The DDR4 config filled all four slots and was pinned to 3200 for it. On
AM5, populating all four slots typically forces the controller down to
3600-4800 MT/s, so 2 × 16 GB at 6000 is the faster configuration despite being
half the DIMMs. The cost is capacity: **32 GB total, down from 64 GB**, which
retires anything that wanted a large resident footprint.

### The iGPU now enumerates as a second ROCm device

New, because the 5950X had no integrated graphics. `ggml_cuda_init` reports
`Device 1: AMD Ryzen 7 9800X3D, gfx1036, VRAM: 15562 MiB` — that is GTT, not
real VRAM. **Measured, it is free:** Qwen3.8-27B at `-ub 1024` gives 1218.2
tok/s with it enumerated and 1223.6 with `HIP_VISIBLE_DEVICES=0`, inside noise.
It is not used for compute and needs no flag. Worth knowing before a future
`-sm`/`-ts` change picks it up by accident, and worth not confusing with the
dGPU when reading `rocminfo`. Note `ROCM_VISIBLE_DEVICES` does **not** filter
the enumeration; `HIP_VISIBLE_DEVICES` does.

## The headline number: +32% bandwidth, not +87%

This is the figure that explains every other table here, so it is worth
measuring rather than assuming. STREAM Triad, 512 MiB per array (well past the
96 MiB L3, so this is DRAM and not cache), best of 10:

| Threads | Triad |
|---|---|
| 1 | 49.4 GB/s |
| 2 | 52.6 GB/s |
| **4** | **53.0 GB/s** |
| 8 | 51.9 GB/s |
| 16 | 50.7 GB/s |

Dual-channel DDR5-6000 is 96 GB/s theoretical. **53.0 is 55% of it.**

**The DIMMs are not the bottleneck — the CCD link is.** The 9800X3D is a
single-CCD part, and the GMI link from the core complex to the IO die saturates
before the memory does. That is why bandwidth peaks at 4 threads and *declines*
past it. Faster DIMMs would not move these numbers; a second CCD would.

The DDR4 box fed the same path at ~40 GB/s. So theoretical bandwidth went up
1.875x while **measured bandwidth went up about a third** — and as the tables
below show, the `-ncmoe` prompt numbers moved +27-37%, tracking the measured
figure and not the theoretical one. (The ~40 GB/s DDR4 figure was recorded
without a stated method, so treat that specific ratio as indicative; the 53.0
is Triad and reproducible.)

## Qwen3.6-35B-A3B — the model this upgrade was for

`llama-bench`, `-ub 1024`, q8_0 KV, pp4096/tg64, `-r 2`.

| `-ncmoe` | Prompt | Gen | Prompt, DDR4 | Δ | Gen, DDR4 | Δ |
|---|---|---|---|---|---|---|
| 40 | **1639.0** | **39.87** | 1198.0 | +36.8% | 31.8 | +25.4% |
| 36 | **1732.6** | **41.71** | 1268.4 | +36.6% | 33.4 | +24.9% |
| 32 | **1852.6** | **43.80** | 1368.0 | +35.4% | 35.7 | +22.7% |
| 28 | **1975.2** | **45.78** | 1472.6 | +34.1% | 35.8 | +27.9% |
| 24 | **2128.2** | **51.05** | 1616.2 | +31.7% | 39.0 | +30.9% |
| 20 | **2298.4** | **54.43** | 1787.3 | +28.6% | 41.9 | +29.9% |
| 16 | **2504.8** | **57.36** | 1974.8 | +26.8% | 43.9 | +30.7% |

Still monotonic, and `-ncmoe 12` still fails to allocate, so 16 remains the
floor — that is a VRAM limit and the card did not change.

**The prompt gain shrinks as `-ncmoe` drops: +36.8% at 40, +26.8% at 16.** That
gradient is the mechanism confirming itself. Fewer expert layers on the CPU
means less host traffic, so there is less for faster memory to win back. At
`-ncmoe 40` the gain lands on the measured +32% bandwidth improvement; by 16
most of the model is GPU-resident and the curve is heading toward the zero that
dense Qwen3.8 actually shows.

### Serving-path check

`llama-bench` is synthetic, so the file's habit is to check it against a real
`llama-server`. The `qwen3.6-32k` preset (`-ncmoe 16`, 32K, `-ub 1024`, q8_0),
700-token code prompt, n=3:

| | run 1 | run 2 | run 3 | `llama-bench` |
|---|---|---|---|---|
| Generation | 58.12 | 58.24 | 58.32 | 57.36 |

Within 1.5%, VRAM 15,106 MiB. Third time the synthetic curve has transferred
without flattering itself.

### Ubatch — the shape is unchanged, the whole curve just moved

`-ncmoe 40`, pp4096:

| `-ub` | Prompt | DDR4 | Δ |
|---|---|---|---|
| 256 | **566.9** | 416.1 | +36.2% |
| 512 *(default)* | **972.5** | 706.0 | +37.8% |
| 1024 | **1639.0** | 1198.0 | +36.8% |

The 256 → 1024 spread is 2.89x, against 2.88x on DDR4. **A uniform scalar
speedup with the shape preserved** — exactly what a pure host-bandwidth change
should look like. The advice is unchanged: raise `-ub` whenever the context
budget allows.

### Generation decay with depth

`-ncmoe 40 -ub 1024`, tg64:

| Depth | Gen | DDR4 | Δ |
|---|---|---|---|
| 0 | **40.96** | 31.8 | +28.8% |
| 32K | **35.65** | 28.8 | +23.8% |
| 131K | **26.47** | 22.2 | +19.2% |

**The gain fades with depth**, because deep generation is increasingly bound by
reading the KV cache out of VRAM rather than by streaming experts from host.
Total decay is slightly *steeper* than before (1.55x against 1.43x) purely
because the shallow end gained more.

## Threads — the old advice now names the collapse case

`-ncmoe 36`, pp512/tg128, `-r 3`:

| `-t` | Prompt | Gen |
|---|---|---|
| 4 | 976.2 | 41.64 |
| 6 | 1035.4 | 42.62 |
| 8 *(default)* | 1054.5 | 43.20 |
| 12 | 1019.4 | 43.47 |
| 16 | 1054.5 | **35.08 ± 0.95** |

The same SMT collapse as the DDR4 box, including the variance blow-up (±0.95
against ±0.08-0.12 elsewhere) — just relocated, because **16 is now *all*
threads where 32 used to be**.

README.md says "leave at 16, never 32". On this CPU **16 is the collapse
case**, and the rule should be read as *never use all SMT threads*, which here
means leave it at the default 8.

**No configuration change is needed.** Nothing hardcodes `-t` in
`models-preset.ini` or `switch-model.sh`, and llama.cpp's default is now 8
because it follows the physical core count. The presets are already correct;
only the prose is stale.

This also has the same root cause as the bandwidth table above: past 4 threads
there is no more bandwidth to win, so extra threads buy only contention.

## Laguna XS.2 — a second MoE, and the head-to-head shifts

`-ub 1024`, q8_0 KV, pp4096/tg64. `-ncmoe 24` is a new row, added to line up
against Qwen3.6's.

| `-ncmoe` | Prompt | Gen | Prompt, DDR4 | Δ | Gen, DDR4 | Δ |
|---|---|---|---|---|---|---|
| 16 | **2548.1** | **63.17** | 2074.9 | +22.8% | 46.7 | +35.3% |
| 20 | **2332.9** | **61.04** | 1846.1 | +26.4% | 43.7 | +39.7% |
| 24 | **2178.2** | **55.51** | — | — | — | — |
| 26 | **2094.4** | **52.15** | 1618.4 | +29.4% | 39.3 | +32.7% |

README.md claims Laguna is faster than Qwen3.6 at every matched `-ncmoe`. **That
survives — but the shape of the lead changed:**

| `-ncmoe` | Laguna pp | Qwen3.6 pp | Margin | Laguna tg | Qwen3.6 tg | Margin |
|---|---|---|---|---|---|---|
| 16 | 2548.1 | 2504.8 | **+1.7%** *(was +5.1%)* | 63.17 | 57.36 | **+10.1%** *(was +6.4%)* |
| 20 | 2332.9 | 2298.4 | +1.5% | 61.04 | 54.43 | +12.1% |
| 24 | 2178.2 | 2128.2 | +2.4% | 55.51 | 51.05 | +8.7% |

**The prompt lead compressed from ~5% to ~2%; the generation lead widened from
~6% to ~10%.**

The cause is the same lighter 512-wide expert FFN that made Laguna fast in the
first place: it was streaming less over the bus, so it had less to win back
(+22.8% at `-ncmoe 16` against Qwen3.6's +26.8%). **Faster host memory helps
the more host-starved model more**, and Qwen3.6 was the more starved of the
two. The practical read: "Laguna wins on prompt" is now a marginal claim worth
about 2%; its durable advantage over Qwen3.6 is generation.

## Gemma 4-26B-A4B — the steepest gradient of the three

The other two MoEs bottom out at `-ncmoe 16`. Gemma runs usefully down to 8,
which extends the range and makes the trend easier to see.

**A method note first.** README.md's Gemma section states only "ROCm, `-fa 1`,
pp4096/tg64" — unlike the Qwen3.6 section, it does not record `-ub` or a KV
type, and the `gemma4-*` presets set neither. So the DDR4 baseline was almost
certainly taken at `llama-bench` defaults (`-ub 512`, f16 KV). The Δ table
below uses those defaults to stay honest; a second run at `-ub 1024`/q8_0
follows so Gemma can be compared with Qwen3.6 and Laguna.

At `llama-bench` defaults, matching the baseline:

| `-ncmoe` | Prompt | Gen | Prompt, DDR4 | Δ | Gen, DDR4 | Δ |
|---|---|---|---|---|---|---|
| 8 | **2392.8** | **62.04** | 1960.6 | +22.0% | 49.8 | +24.6% |
| 12 | **2099.8** | **54.64** | 1603.6 | +30.9% | 42.6 | +28.3% |
| 20 | **1769.4** | **43.39** | 1276.0 | +38.7% | 33.9 | +28.0% |

**+22.0% → +38.7% as offload rises.** That is the same gradient Qwen3.6 and
Laguna show, over a wider span, and it is the clearest single demonstration in
this file that the gain is bought with host traffic: at `-ncmoe 8` most of the
model is on the GPU and DDR5 barely matters; at 20 it matters a third.

At `-ub 1024` and q8_0 KV, comparable with the other two MoEs:

| `-ncmoe` | Prompt | Gen |
|---|---|---|
| 8 | **3187.9** | 58.28 |
| 12 | **2888.6** | 51.75 |
| 16 | **2693.1** | 45.54 |
| 20 | **2542.4** | 41.91 |

`-ub 1024` is worth +33% prompt here (2392.8 → 3187.9 at `-ncmoe 8`), while
q8_0 KV costs generation against f16 (62.04 → 58.28) — both consistent with the
existing tuning findings, neither changed by the new memory.

At the one matched point against the others (`-ncmoe 16`, `-ub 1024`, q8_0):

| Model | Prompt | Gen |
|---|---|---|
| **Gemma 4-26B-A4B** | **2693.1** | 45.54 |
| Laguna XS.2 | 2548.1 | **63.17** |
| Qwen3.6-35B-A3B | 2504.8 | 57.36 |

Gemma takes prompt — it is the smallest of the three at 25.2B against 33.4B and
34.7B — but loses generation badly, which is the non-hybrid attention showing
up as a fat KV cache on every generated token.

### The flattest-curve claim survives

Depth sweep at `-ncmoe 8`, tg64, defaults:

| Depth | Gen | DDR4 | Δ |
|---|---|---|---|
| 0 | **63.29** | 51.4 | +23.1% |
| 8K | **59.65** | 49.0 | +21.7% |
| 16K | **58.49** | 47.5 | +23.1% |
| 32K | **56.86** | 47.0 | +21.0% |

Total decay 10.2% across the range, against 8.6% on DDR4 — still by some way
the flattest curve here (Qwen3.6 loses 15% to 32K, dense Qwen3.8 17% at q8_0).

**The gain is uniform with depth (+21-23%), which Qwen3.6's is not** (+29%
shallow fading to +19% at 131K). At `-ncmoe 8` there is little expert streaming
for depth to compete with, so nothing shifts the balance as the KV cache grows.
Qwen3.6 at `-ncmoe 40` is streaming heavily, so deep generation progressively
hands the bottleneck back to VRAM.

## GLM-4.7-Flash — the exception that sharpens the rule

`deepseek2` arch, MLA attention, 47 layers. `-ub 1024`, q8_0 KV, pp4096/tg64,
`-r 2` — the same method as the baseline.

| `-ncmoe` | Prompt | Gen | Prompt, DDR4 | Δ | Gen, DDR4 | Δ |
|---|---|---|---|---|---|---|
| 28 | **1446.3** | **39.40** | 1243.6 | **+16.3%** | 28.7 | +37.3% |
| 24 | **1493.1** | **41.65** | 1318.7 | **+13.2%** | 32.3 | +28.9% |
| 20 | **1535.7** | **46.59** | 1375.6 | **+11.6%** | 35.9 | +29.8% |
| 16 | **1588.2** | **50.76** | 1463.2 | **+8.5%** | 39.0 | +30.2% |
| 12 | **1654.8** | **55.13** | 1571.9 | **+5.3%** | 43.3 | +27.3% |

**Generation behaves exactly like the other three MoEs (+27-37%). Prompt does
not — it gains only +5.3% to +16.3%, against +22-39% everywhere else.**

The gradient still points the right way (more offload, more gain), but the
magnitude is a third of what Qwen3.6 and Gemma show. The cause is MLA: GLM's
prompt path is bound by attention compute on the GPU, not by streaming experts
from host, so faster memory has little to accelerate. README.md already
recorded the symptom without the cause — GLM's 8.5x prompt decay over 32K,
"the one clearly worse number for GLM against everything else in this file".
That steepness and this small prompt gain are the same fact seen from two
directions.

Notice also that prompt now varies only 14% across the entire `-ncmoe` sweep
(1446 → 1655) where on DDR4 it varied 26% (1244 → 1572). Removing the memory
bottleneck made GLM's prompt path *more* visibly GPU-bound, not less.

### Depth sweep, `-ncmoe 12` (the 32K preset)

| Depth | Prompt | DDR4 | Δ | Gen | DDR4 | Δ |
|---|---|---|---|---|---|---|
| 0 | **1657.5** | 1608.2 | +3.1% | **54.74** | 42.2 | +29.7% |
| 8K | **549.3** | 562.9 | **−2.4%** | **48.21** | 39.3 | +22.7% |
| 16K | **330.8** | 338.8 | **−2.4%** | **42.13** | 35.7 | +18.0% |
| 32K | **183.5** | 190.2 | **−3.5%** | **33.66** | 29.5 | +14.1% |

**Prompt at depth did not improve at all — it went slightly backwards**, while
generation at the same depths gained 14-30%. On one model, in one table, the
two operations split cleanly: the host-bound one gains, the GPU-bound one does
not.

**This independently corroborates the Qwen3.8 regression.** Dense Qwen3.8 — the
other GPU-bound workload measured here — came in 4.8-8.4% down. GLM's
prompt-at-depth is 2.4-3.5% down. Two unrelated models, same direction, both
on GPU-bound paths, while every host-bound path in this file gained. That is
the signature of a small GPU-side regression, which points at the kernel
(7.1.5 → 7.2.6) rather than anything to do with the memory.

GLM's weak spot is unchanged: prompt decay is **9.0x** over 32K against 8.5x
before, still far steeper than the hybrid-attention Qwen models. The upgrade
does not fix it, and for agentic use — where most of the token cost is prompt,
not generation — that remains the number to weigh.

## Qwen3.8-27B — the control, and it stayed put

Dense, 64 layers, fully GPU-resident at `-ngl 99`. No expert offload, so there
is no host traffic for faster RAM to accelerate, and the prediction is that it
should not move at all.

q8_0 KV, pp4096/tg64, `-r 2`, on the **v2** file that the DDR4 baseline used:

| `-ub` | Prompt | Gen | Prompt, DDR4 | Δ | Gen, DDR4 | Δ |
|---|---|---|---|---|---|---|
| 256 | **1124.3** | **30.40** | 1180.7 | −4.8% | 31.9 | −4.7% |
| 512 | **1172.2** | **30.39** | 1279.7 | −8.4% | 31.9 | −4.7% |
| 1024 | **1218.2** | **30.43** | 1306.9 | −6.8% | 31.9 | −4.6% |

**It behaved as a control should: none of Qwen3.6's +27-37% appears.** Read
against the two MoE tables, this pair is the cleanest evidence in the record
that `-ncmoe` throughput is a host-bandwidth measurement and not a general
speed measurement.

### Measure v2 against v2

A first pass used `UD-Q3_K_XL-v3` and showed −11%. That is a quant-version
artefact, not a hardware result — the DDR4 baseline was taken on the Dynamic
2.0 file, before the in-place re-quant. v3 on DDR5 measures 1064.2 / 1119.9 /
1163.0 with tg 29.5. The two files are not comparable; see the Dynamic 3.0
section in README.md.

### The ~6% regression is real, and is not the RAM

Reproducible across both quant versions and all ubatch sizes, σ ≤ 1.1. Ruled
out:

- **ROCm** — `hipconfig` reports `7.2.53211-3d9ef42`, identical; `libggml-hip.so`
  untouched since the Aug 17 build
- **PCIe** — 32.0 GT/s x16, at max, not degraded
- **The model file** — same GGUF, and v2/v3 both regress
- **llama.cpp** — same commit `7c35571e5`
- **The new iGPU** — hiding it gives 1223.6 vs 1218.2, inside noise

The remaining uncontrolled variable is the **kernel, 7.1.5 → 7.2.6**. A dense
GPU-resident model has no host path to get slower on, so this is logged as an
open amdgpu question rather than attributed to the CPU or the RAM. Not chased;
`linux-cachyos-lts` 6.18.52 is installed and would A/B it if it ever matters.

**GLM-4.7-Flash corroborates it.** Its prompt-at-depth — the other GPU-bound
path measured here, and a completely different architecture — is also down,
2.4-3.5%, while its generation gained 14-30% at the same depths. Two unrelated
models, both GPU-bound, both slightly negative, in a session where every
host-bound number rose. That is a GPU-side regression, not a memory effect.

## What this means

### The gain is paid out per operation, not per model

Four MoEs and one dense control, prompt gain against `-ncmoe`:

| Model | Low offload | High offload | Gradient |
|---|---|---|---|
| Gemma 4-26B-A4B | +22.0% *(`-ncmoe 8`)* | +38.7% *(20)* | **+16.7 pts** |
| Qwen3.6-35B-A3B | +26.8% *(16)* | +36.8% *(40)* | +10.0 pts |
| Laguna XS.2 | +22.8% *(16)* | +29.4% *(26)* | +6.6 pts |
| **GLM-4.7-Flash** *(MLA)* | **+5.3%** *(12)* | **+16.3%** *(28)* | +11.0 pts |
| Qwen3.8-27B *(dense)* | — | **0%** *(no offload)* | — |

Generation, by contrast, is uniform across all four MoEs — **+23% to +40%,
including GLM** — with no comparable spread.

The first three models plus the dense control suggest a simple rule: the gain
scales with how much of the model sits in system RAM. **GLM shows that is the
wrong unit.** It offloads as much as the others and gains generation just like
them, but its prompt barely moves, because MLA attention makes *that specific
operation* GPU-compute-bound. The correct statement is:

> The gain is proportional to how much of **the operation you are measuring**
> is host-bandwidth-bound — not to how much of the model is offloaded.

Same model, same `-ncmoe`, two operations, two completely different answers.
The ceiling where an operation is fully host-bound lands at **+37-39%**, near
the measured +32% bandwidth improvement with the rest attributable to the
faster cores and the 96 MiB L3. Where it is GPU-bound, the answer is zero or
slightly negative.

- **CPU-offloaded MoE generation is where the money went**, on every model
  tested: Qwen3.6 +23-31%, Laguna +33-40%, Gemma 4 +25-28%, GLM +27-37%.
- **Prompt depends entirely on the attention design.** Hybrid/standard
  attention gains +22-39%; GLM's MLA gains +5-16% shallow and **nothing at
  depth**.
- **Dense, fully GPU-resident models gained nothing**, as predicted. If your
  working set fits in 16 GB of VRAM, this upgrade was not for you.
- **The ceiling is the CCD, not the DIMMs.** 53.0 GB/s of a theoretical 96.
  Faster memory would not help; more CCDs would.
- **`-t` advice changed from 16 to 8**, and the presets already do the right
  thing on their own.
- **Capacity halved, 64 GB → 32 GB.** Worth checking before loading anything
  large: `Laguna-XS-2.1-Q8_0.gguf` alone is 35.6 GB and now exceeds total RAM.

## Reproducing

```sh
# host bandwidth
gcc -O3 -march=native -fopenmp -o triad benchmarks/triad.c && OMP_NUM_THREADS=4 ./triad

# MoE sweep
llama-bench -m models/Qwen3.6-35B-A3B-UD-Q4_K_M.gguf -ngl 99 -fa 1 \
  -ncmoe 40,36,32,28,24,20,16 -ub 1024 -ctk q8_0 -ctv q8_0 -p 4096 -n 64 -r 2

# dense control
llama-bench -m models/Qwen3.8-27B-UD-Q3_K_XL.gguf -ngl 99 -fa 1 \
  -ub 256,512,1024 -ctk q8_0 -ctv q8_0 -p 4096 -n 64 -r 2

# threads
llama-bench -m models/Qwen3.6-35B-A3B-UD-Q4_K_M.gguf -ngl 99 -fa 1 -ncmoe 36 \
  -ctk q8_0 -ctv q8_0 -p 512 -n 128 -t 4,6,8,12,16 -r 3

# Gemma 4 at baseline defaults (no -ub / no KV flags), plus its depth sweep
llama-bench -m models/gemma-4-26B-A4B-it-UD-Q4_K_M.gguf -ngl 99 -fa 1 \
  -ncmoe 8,12,20 -p 4096 -n 64 -r 2
llama-bench -m models/gemma-4-26B-A4B-it-UD-Q4_K_M.gguf -ngl 99 -fa 1 -ncmoe 8 \
  -p 0 -n 64 -d 0,8192,16384,32768 -r 2

# GLM-4.7-Flash sweep and depth sweep
llama-bench -m models/GLM-4.7-Flash-UD-Q4_K_XL.gguf -ngl 99 -fa 1 \
  -ncmoe 28,24,20,16,12 -ub 1024 -ctk q8_0 -ctv q8_0 -p 4096 -n 64 -r 2
llama-bench -m models/GLM-4.7-Flash-UD-Q4_K_XL.gguf -ngl 99 -fa 1 -ncmoe 12 \
  -ub 1024 -ctk q8_0 -ctv q8_0 -p 4096 -n 64 -d 0,8192,16384,32768 -r 2
```
