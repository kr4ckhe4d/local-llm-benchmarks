## In-session follow-up turns (the number you actually feel)

WARM_s above is a *fresh session*: two separate `claude -p` invocations. Claude
Code varies cwd/date/session-id inside the prompt, so the prefixes differ and
the cache misses. A real conversation shares a long stable prefix. Measured
with `--continue` in one session:

  model                        turn 1     turn 2 (--continue)
  laguna-33B-A3B-128k            25.5s          3.1s
  qwen3.6-35B-A3B-128k           58.6s         31.9s

Laguna drops 8x. Qwen3.6 only halves -- it is a thinking model
(reasoning-budget 1024) and spends turn 2 generating, not prefilling: it
emitted 507 output tokens against Laguna's 171 in the table above. So the gap
is generation, not prompt handling. Treat that as the likely cause rather than
a measured one; it was not isolated.

## Retracted: "hybrid attention prevents prefix caching"

An earlier reading of this data claimed sliding-window models get no prefix
reuse, on the grounds that GLM reported cache_read>0 while Laguna reported 0.
That was wrong, and the controlled test that killed it is worth keeping.

Two byte-identical requests straight to /v1/messages, no client in between:

  model                        1st       2nd (identical)
  laguna-33B-A3B-128k          65.3s     0.1s   cache_read=48255
  qwen3.6-35B-A3B-128k         37.2s     0.3s   cache_read=48134
  glm-4.7-flash-30B-A3B-128k  214.6s     0.4s   cache_read=48129

Prefix caching works on every model tested, including Laguna's hybrid
SWA -- a 650x speedup. The per-model cache_read differences seen through
Claude Code came from its multiple internal API calls per invocation, not from
attention architecture. `usage` in the Claude Code result envelope aggregates
those calls, so it was never a valid basis for a per-request claim.

The lesson generalises: do not infer server behaviour from a client's usage
accounting. Measure the server directly.
